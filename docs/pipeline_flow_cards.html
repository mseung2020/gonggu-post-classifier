포스트 하나가 인스타·유튜브에 올라온 순간부터
DB에 확정 링크로 저장되기까지

전체 7단계입니다. 1~5는 새로 올라온 포스트를 처음부터 끝까지 처리하는 본줄기이고, 6~7은 이미 처리된 것 중 상태가 바뀐 것만 골라 매일 다시 손보는 보강 단계입니다. 모든 LLM 판단(2·4단계)은 이제 외부 워크플로우 없이 자체 코드가 직접 호출합니다 — 그래서 동시 처리량도 훨씬 크게 늘었습니다. 2번 옆에는 "공구"라는 단어 없이도 사실상 그룹특가인 유튜브 PPL 영상을 따로 잡아내는 독립 소스가 하나 더 합류합니다.

유튜브 PPL 별도 수집·분류

fetch_yt_ppl.py · classify_yt_ppl.py

"공구"/"공동구매" 키워드가 없어서 1~2단계가 원천적으로 못 보는 영상이 있습니다 — 브랜드 협찬(PPL)으로만 표시됐지만 실제로는 그룹특가인 경우입니다. 그래서 hifen DB의 brand 테이블에서 공구 키워드가 없는 영상만 따로 가져와, 전용 LLM으로 "PPL이지만 사실상 그룹특가인지"를 판별합니다. 1~2단계 코드는 이미 검증된 로직이라 전혀 손대지 않고, fetch·프롬프트·스크립트를 전부 새로 분리했습니다.

링크 해석

resolve_links (패키지)

후보 링크들을 실제로 열어봐서 "진짜 구매 가능한 최종 링크 1개"로 확정합니다. 링크인바이오 허브(인포크 등)면 가볍게 구조화 데이터로 먼저 훑고, 아니면 브라우저로 열어 LLM이 상품페이지인지 판별합니다.

입력
03_load_ready 중
미해석 상품
처리
Playwright +
자체 LLM#2·#3
출력
04_resolved/<날짜>.jsonl
cd scripts && RESOLVE_CONCURRENCY=30 python3 -m resolve_links
cd scripts && python3 -m resolve_links 50# 50건만 테스트
알아둘 점
  • LLM#2(링크선택)·LLM#3(페이지판별)도 LLM#1과 마찬가지로 외부 워크플로우 없이 자체 코드에서 직접 호출합니다 — 판단 자체는 빨라졌지만, 이 단계가 느린 진짜 이유는 아래 두 개(브라우저·안티봇)입니다.
  • 워커 1개 = 브라우저 1개라 메모리를 많이 씁니다. 컴퓨터 사양에 맞춰 동시성을 조절하고, 다른 무거운 앱이 떠 있으면 여유 메모리를 확인할 것 — LLM 호출과 달리 이 제약은 그대로입니다.
  • MAX_PER_DOMAIN(기본 4)이 같은 목적지 도메인에 동시에 몰리는 걸 막습니다 — 실제로 페이지를 여는 순간 기준이라, 가벼운 1차 홉이 무거운 2차 홉의 보호를 깎아먹지 않습니다.
  • python3 scripts/login_naver.py로 네이버 로그인 세션을 저장해두면, 로그인월로 튕기던 페이지를 실제 계정으로 우회할 수 있습니다.
  • 같은 목적지 URL(같은 인플루언서 계정)을 형제 상품들이 자주 공유해서, 프로세스 안에서 한 번 요청한 URL은 캐시해 재사용합니다.
  • 동시에 두 번 실행하지 말 것 — 도메인당 제한이 프로세스 하나 안에서만 관리됩니다.

진행중 공구 링크 재탐색

rescan_inprogress.py

공구가 "시작전"일 때는 인포크 등에 아직 실제 구매 링크가 안 걸려 있어서 못 찾는 경우가 많은데, "진행중"이 되면 그 링크가 채워지는 경우가 많습니다. 그래서 지금 진행중인데 아직 못 찾은(unresolved) 상품만 골라 4단계와 같은 방식으로 다시 시도합니다.

입력
DB에서 직접 조회
(파일 안 거침)
처리
4단계와 동일한
판단/크롤링 로직
출력
done이면 해당 행
UPDATE
RESCAN_CONCURRENCY=6 python3 scripts/rescan_inprogress.py
알아둘 점
  • 6번(공구 상태 갱신) 다음에 실행해야 합니다 — 오늘자 "진행중" 상태가 먼저 확정돼 있어야 그걸 기준으로 대상을 고를 수 있습니다.
  • 여전히 unresolved면 그대로 둡니다 — 다음 재탐색까지는 어쩔 수 없는 것으로 처리합니다.
  • 4단계(resolve_links)와 동시에 돌리지 말 것 — 같은 이유(도메인 제한이 프로세스별로 따로 관리됨)입니다.

매일 실행 순서 요약

위 1~7번을 이 순서 그대로, 하루에 한 번 실행합니다. 6번이 5번보다 먼저 와야 그날의 "진행중" 상태가 확정되고, 7번이 그걸 기준으로 재탐색 대상을 고를 수 있습니다. 2번 다음의 ＋ 두 줄(유튜브 PPL 별도 소스)은 번호가 없지만 매일 같이 돌려야 하는 명령입니다 — 3번이 처리하는 02_classified에 그 결과가 같이 들어가기 때문입니다.
