# 공구왕 포스트 분류 파이프라인

인스타그램/유튜브 원본 데이터에서 "확실한 공구(공동구매)"만 최대한 보수적으로 걸러내
상품 단위로 정규화해 저장하는 데이터 파이프라인입니다. 하루 수만 건의 소셜 게시물을 읽어서
그중 실제로 판매 링크가 확정된 공구 상품만 남기는 것이 목표이고, **범위는 "구매 링크를
하나로 확정하는 것까지"** — 그 링크를 열어 가격/이미지 같은 실제 상품 데이터를 가져오는 건
이 결과를 읽어가는 다음 단계의 책임입니다.

이 문서는 사용법 나열보다 **왜 이렇게 짰는지**를 설명합니다. 운영 중에 쌓인 세부 튜닝값과
날짜별 실측 기록은 이 쇼케이스에는 없습니다 — 코드 안 주석에 그대로 남아 있습니다.

## 파이프라인 — 큰 그림

```
hifen DB (읽기 전용)
   │  키워드 매칭("공구"/"공동구매")으로 후보 포스트만 SQL에서 미리 좁힘
   ▼
① fetch_source            원본 그대로 저장, 아직 아무 판단 없음
   ▼
② classify        LLM#1 — 공구 여부 / 상품 배열 / 시작·종료일 추출
   ▼
③ transform        코드 게이트 — "확실한 것만" 보수적으로 필터링 (LLM 재호출 없음)
   ▼
④ resolve_links    크롤링 → LLM#3(페이지 판별) → 필요하면 LLM#2(링크 선택) → 링크 1개 확정
   ▼
⑤ load             DB 적재 (이미 있는 행은 skip, UPDATE 없음)

──────── 여기서부터는 "이미 적재된 것"을 매일 다시 손보는 보강 단계 ────────

⑥ update_gonggu_stage    오늘 날짜 기준으로 시작전 → 진행중 → 종료 갱신
⑦ rescan_inprogress      "진행중"인데 아직 링크를 못 찾은 상품만 재탐색
⑧ backfill_period        캡션에 날짜가 없어 기간 미상으로 남은 상품 보강
```

①~⑤가 "새 포스트를 처음부터 끝까지 처리"하는 본줄기, ⑥~⑧은 "상태가 바뀐 것만 골라
다시 손보는" 보강 단계입니다. 여기에 유튜브 PPL(브랜드 협찬 영상 중 사실상 그룹특가인 것)을
찾는 완전히 독립된 유입 경로가 하나 더 있어서, `③ transform`부터 본줄기와 합류합니다.

## 설계가 왜 이런 모양인가

### 1. 모든 단계는 파일이자 체크포인트다

각 단계는 이전 단계의 출력 폴더(`01_raw` → `02_classified` → `03_load_ready` → `04_resolved`)를
읽어 다음 폴더에 씁니다. 폴더 이름 자체가 "어디까지 처리됐는지"를 말해주고, 레코드 1개 =
JSONL 1줄이라 `grep`/`head`로 바로 들여다볼 수 있습니다. append-only라 저장 비용이 건수에
비례해 늘지 않고, 중단됐다 다시 돌려도 이미 처리된 건 자동으로 건너뜁니다.

이게 중요한 이유는 이 파이프라인이 **하루에 수만 번 LLM을 호출한다**는 것입니다. 체크포인트가
없으면 스크립트 하나가 중간에 죽었을 때 이미 쓴 토큰을 몽땅 다시 태워야 합니다. 여기서는
"재실행 = 안전"이 기본 전제라, 스케줄러도 크게 고민할 게 없습니다 — 매일 같은 명령을 실행하고,
실패하면 실패한 지점부터 다시 실행하면 됩니다.

### 2. 게이트링은 LLM이 아니라 코드가 한다

`② classify`(LLM#1)는 판단만 붙이고 아무것도 거르지 않습니다. 실제로 "이건 공구가 아니다"를
결정하는 `③ transform`은 순수 규칙 기반이라 LLM 호출이 없고, 빠르고, 결정론적이고, 필터링
기준을 코드 리뷰로 검증할 수 있습니다. LLM은 "이 게시물이 공구처럼 보이는가"라는 애매한
판단에, 코드는 "그 판단을 받아들일지"라는 정책 결정에 쓰는 것 — 판단과 정책을 같은 곳에
두지 않았습니다.

필터링 자체도 정밀도(precision) 쪽으로 크게 기울어 있습니다. 상품을 하나도 특정 못 하면
공구 자체를 통째로 버리고(빈 배열 금지 — 애매하면 `is_gonggu`를 재검토), 날짜는 캡션에 명시된
경우에만 채우고 추측하지 않습니다. 커머스 데이터에서는 "놓친 공구"보다 "아닌데 공구로 잘못
들어간 건"이 훨씬 비쌉니다 — 후자는 다음 단계 전체(가격 조회, 상품 매칭)를 오염시킵니다.

### 3. 링크 해석은 비용순으로 계단식이다

`④ resolve_links`가 이 파이프라인에서 제일 복잡한 단계인데, 이유는 "구매 링크 1개"를
확정하는 방법이 경우마다 다르기 때문입니다:

```
프로필 링크가 구조화된 "링크인바이오" 허브(인포크/링크트리 등)인가?
  ├─ 예, 파서가 있는 호스트 → 브라우저 없이 구조화 데이터로 후보 추출 (제일 쌈)
  ├─ 예, 파서는 없지만 허브인 게 확실 → 브라우저는 열되 LLM 호출은 생략
  └─ 아니오/모르겠음 → 브라우저로 열어서 LLM에게 "이 페이지 뭐야?" 판별 (제일 비쌈)
```

같은 인플루언서를 여러 상품이 공유하는 경우가 흔해서(같은 URL을 프로세스 안에서 캐싱),
그리고 안티봇 회피 대기가 상품마다 붙어서, 이 단계의 실제 처리 속도는 "몇 퍼센트가 제일 싼
경로로 빠지는가"에 좌우됩니다. 그래서 설계 원칙은 **비싼 경로(브라우저+LLM)로 가기 전에
쌀 수 있는 모든 탈출구를 먼저 확인**하는 것이고, `httpfetch.py`(브라우저 없는 HTTP 패스트
패스)나 링크인바이오 호스트 목록 같은 코드가 전부 그 탈출구입니다.

### 4. 안티봇은 "우회"가 아니라 "격리"로 다룬다

네이버 스마트스토어 같은 곳은 자동화 접근을 로그인월/캡차로 막습니다. 이 저장소가 택한
방식은 두 갈래입니다 — **대량 무인 경로(daily)는 절대 우회를 시도하지 않고** 막히면
`unresolved`로 정직하게 남기고, **사람이 곁에 있는 별도 패스**(`reverify_uc`)가 실제 로그인
세션을 가진 크롬으로 그 건들만 낮은 동시성·시간 예산 안에서 다시 시도합니다. undetected
브라우저 엔진을 대량 동시 실행에 섞었다가 겪은 반복 크래시가 이 분리의 직접적인 이유입니다 —
"차단을 뚫는 코드"와 "차단당하면 정직하게 포기하는 코드"를 같은 실행 경로에 두지 않았습니다.

### 5. 오케스트레이터는 단계 레지스트리다

`daily.py`는 파이프라인 단계를 순서가 있는 선언적 리스트(`id`/`env`/`critical`/`needs_uc`)로
갖고 있습니다. 본줄기 단계는 실패하면 즉시 멈추고(뒤 단계가 앞 단계 산출물에 의존하므로),
보강 단계는 서로 독립이라 하나가 실패해도 나머지는 계속 돕니다. 크롤링 드라이버가 먹통이 되는
것과 "설정 실수로 죽는 것"을 구분해서 전자만 자동 재시도하고, 브라우저 풀을 정기적으로
재기동하되 진행 중이던 작업은 마치고 재기동하도록(드레인) 만들어서 재작업 비용을 없앴습니다.
"단계 하나를 어떻게 실행할지"와 "단계들을 어떤 순서·정책으로 이어붙일지"를 분리해 둔 덕에,
이 리스트에 새 단계를 추가하는 비용이 낮습니다 — 실제로 손으로 치던 이메일 동기화·uc 재검증
패스가 나중에 이 레지스트리에 그대로 얹혔습니다.

### 6. 옛 경로를 절대 깨지 않고 재구성한다

파이프라인이 자라면서 책임별 하위 패키지(`pipeline/`/`category/`/`infra/`/`tools/`)로
재구성했는데, 매일 손으로 입력하는 실행 명령(`python3 -m gonggu.classify` 등)과 이미 걸려
있는 배포 스크립트(`pyproject.toml`의 진입점)를 깨뜨릴 수 없었습니다. 그래서 옮긴 모듈의
옛 경로에는 `sys.modules` 자체를 새 위치의 모듈로 바꿔치기하는 얇은 호환 shim만 남겼습니다 —
`import *`가 아니라 이 방식을 쓴 이유는 밑줄로 시작하는 내부 이름까지 안전하게 넘어가야 했기
때문입니다. 실행 경로를 하나도 안 바꾸고 코드 구조만 바꾸는 리팩터가 가능하다는 것이
이 패턴의 요점입니다.

## 저장소 구조

| 위치 | 책임 |
|---|---|
| `gonggu/pipeline/` | 위 다이어그램의 본줄기 + 보강 단계, `daily.py`가 순서대로 실행 |
| `gonggu/resolve_links/` | 링크 해석 — 계단식 판별 로직만 따로 뗀 하위 패키지 |
| `gonggu/enrich_detail/` | (파이프라인 뒷단, 별도 운영) 확정된 링크를 열어 상세 데이터 보강 |
| `gonggu/linkbio_parser/` | 링크인바이오 호스트별 구조화 파서 모음 |
| `gonggu/category/` | 이 파이프라인과 독립적인 제품 카테고리 분류(LLM#4) |
| `gonggu/infra/` | DB 연결, LLM 호출, 크롤 워커 풀 등 여러 단계가 공유하는 배관 |
| `gonggu/tools/` | 진단 대시보드, 비용 리포트 등 사람이 필요할 때 돌리는 도구 |
| `queries/` | DB 스키마 DDL과 마이그레이션 SQL |

`gonggu/classify.py`처럼 하위 패키지 이름이 안 붙은 옛 경로들은 위 "옛 경로를 절대 깨지 않고
재구성한다"에서 설명한 호환 shim입니다 — 새로 코드를 추가할 땐 하위 패키지 쪽에 쓰세요.

## 설치

```bash
pip install -r requirements.txt
playwright install chromium   # resolve_links(링크 해석 단계)용, 최초 1회
cp .env.example .env          # DB 자격증명 + DEEPSEEK_KEY 채우기
pip install -e .              # (선택) gonggu-classify 같은 짧은 명령을 쓰려면
```

DB 스키마는 `queries/create_gonggu_tables.sql`을 적용하면 됩니다(기존 데이터를 건드리지 않는
안전한 신규 설치용 — DROP은 `queries/reset_gonggu_tables.sql`에 별도로 있습니다).

모든 모듈은 저장소 루트에서 `python3 -m gonggu.<모듈>`로 실행합니다(예:
`python3 -m gonggu.classify`, `python3 -m gonggu.resolve_links`). 매일 전체를 순서대로
돌리려면 `python3 -m gonggu.daily` 한 줄이면 됩니다 — 각 단계의 환경변수 기본값과 실행
순서는 `python3 -m gonggu.daily --list`로 확인할 수 있습니다.

## LLM

전부 DeepSeek API를 직접 호출합니다 — 외부 워크플로우 도구 없이 프롬프트와 호출 로직이
`gonggu/infra/prompts.py` / `gonggu/infra/common.py`에 코드로 그대로 있습니다. 역할별로
프롬프트가 완전히 분리되어 있습니다(공구 판별 / 링크 선택 / 페이지 판별 / 카테고리 분류 /
유튜브 PPL 판별 — 서로 절대 공유하지 않음).

## 검증

이 파이프라인은 599개의 pytest 테스트로 검증되어 있습니다 — 체크포인트 파싱·재시도 로직·
게이트링 규칙 같은 순수 로직은 물론, 실제 크롤링/LLM 호출 없이 오케스트레이터의 제어 흐름
(단계 실패 시 중단/계속 판단, uc 게이트 3분기, 호환 shim의 동일성)까지 커버합니다. 이
쇼케이스 브랜치에는 테스트 코드 자체를 포함하지 않았습니다.
